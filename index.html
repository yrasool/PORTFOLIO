Lab Note / Browser Rendering

Why Pretext matters if you care about browser performance, not just typography.

If you only see a text-layout library, the release does not look like a big deal. The context is browser layout cost. That is where the idea becomes interesting.

Core Idea

When you write width: 300px on a div, the browser still decides where the text wraps, which word moves to the next line, how tall the block becomes, and how spacing behaves. That layout work is expensive. Pretext shifts text measurement out of DOM layout and into a canvas-based prepare step, so future layout passes become cached math instead of reflow.

01

The browser owns line breaks by default

Long text wrapping is not something CSS fully specifies line by line. The rendering engine resolves font metrics, spacing, bidirectional text, and line breaking during layout.

02

DOM measurement can trigger reflow

Asking the DOM how large text is can force the browser to run that layout pipeline again. Once is usually fine. Doing it repeatedly across many nodes can become a real performance problem.

03

Pretext caches the expensive part

The first prepare() pass is still expensive because measurement has to happen somewhere. After that, resize and relayout work can come from cached values, which means less browser layout churn and more predictable math.
